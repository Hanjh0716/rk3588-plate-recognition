## 3. ⭐ 核心：检测模型的输出长什么样

你的模型输出（你亲手跑出来的）：

```
输出0: shape=(1, 255, 80, 80)
输出1: shape=(1, 255, 40, 40)
输出2: shape=(1, 255, 20, 20)
```

### 3.1 先把 255 拆开

```
255 = 3 × 85
       │    └── 85 = 5 + 80
       │              │    └── 80 个类别分数（COCO 数据集：人、自行车、汽车、猫、狗…共 80 类）
       │              └──── 5 个数：(cx, cy, w, h, obj_conf)
       │                       前 4 个是"框在哪、多大"，第 5 个是"这里有没有东西"的置信度
       └──────── 3 个 anchor（每个格子预设 3 种形状的先验框）
```

### 3.2 三个尺度分别在干什么

| 输出 | 网格 | 步长 stride | 负责 | 一个格子代表原图多大 |
|---|---|---|---|---|
| (1,255,**80**,**80**) | 80×80 | 8 | **小目标** | 8×8 像素 |
| (1,255,**40**,**40**) | 40×40 | 16 | 中目标 | 16×16 像素 |
| (1,255,**20**,**20**) | 20×20 | 32 | 大目标 | 32×32 像素 |

**为什么要分三个尺度？**
一个 8×8 的网格"看不住"一辆大巴（感受野不够）；一个 32×32 的网格"看不清"一个小车牌（分辨率不够）。

> **对你的项目最重要的一个判断**：车牌在整张图里是**中小目标**，
> 所以 `(1,255,80,80)` 这一支 + 中尺度那一支是主力，20×20 那一支基本用不上。
> 以后调模型、看漏检时，**先去查 80×80 这一支的分数**。

### 3.3 一共多少个候选框？

```
80×80×3  = 19200
40×40×3  =  4800
20×20×3  =  1200
────────────────────
合计      = 25200 个候选框
```

**后处理的全部工作，就是在这 25200 个里挑出真正的框。**
一张图 25200 个候选 → 最后留 1 个（车牌）——这就是"检测"的全过程。

## 4. ⭐ 后处理三件套（你要写的代码全在这一节）

### 4.1 解码 decode：把"偏移量"算成"真实坐标"

模型输出的**不是绝对像素坐标**，而是"相对这个网格单元的偏移量"。

```python
# 对 80×80 这一支（stride=8）
x = (sigmoid(tx) * 2 - 0.5 + grid_x) * stride
y = (sigmoid(ty) * 2 - 0.5 + grid_y) * stride
w = (sigmoid(tw) * 2) ** 2 * anchor_w
h = (sigmoid(th) * 2) ** 2 * anchor_h
```

逐个解释：

| 部分 | 什么意思 |
|---|---|
| `sigmoid(v)` | 把任意实数压到 **0~1**。模型输出可以是任意值，但"比例"必须在 0~1 之间 |
| `grid_x / grid_y` | 这个格子在第几列、第几行（0…79） |
| `* 2 - 0.5` | YOLOv5 特有：让框的**中心可以超出格子**（否则框中心永远被锁在格子内） |
| `** 2` | YOLOv5 特有：保证宽高**恒为正**（平方不可能为负），同时放大差异 |
| `* stride` | 把"格子单位"换算回"640 图的像素单位" |

**记住这一句**：模型学的不是"框在哪"，而是"**相对周围格子，框应该偏多少、多大**"。
这是一种"从先验框出发做微调"的思路——比直接回归绝对坐标容易学得多。

### 4.2 置信度过滤

```python
conf = obj_conf * class_score
```

- `obj_conf` = "这个格子里有东西吗"
- `class_score` = "如果有，是这一类吗"
- **相乘**才是"这里有一个车牌"的总可信度

```python
keep = conf > 0.25        # 过滤，25200 个瞬间变成几十个
```

**为什么用乘法**：两个条件必须**同时**成立。相加会让"很像但其实没有东西"的框蒙混过关。

### 4.3 NMS 非极大值抑制 —— 一次讲透

**要解决的问题**：一个车牌周围会冒出几百个框，它们指着**同一件事**。
**做法**：谁的分数最高就信谁，把和他重叠太多的全删掉。

```
① 25200 个框按置信度从高到低排序
② 取出第 1 名 → 定为"结果"
③ 和它 IoU > 0.45 的（重叠太多的）全部删掉   ← 这一步通常一次删掉几百个
④ 回到 ②，取剩下的第 1 名 → 重复，直到没有框
```

**IoU（交并比）** = 两个框的交集面积 ÷ 并集面积

```
   ┌────────┐
   │  A ┌───┼────┐        交集面积 = 中间那块
   │    │   │    │        IoU = 交集 / 并集
   └────┼───┘    │
        └────────┘        0 = 完全不相干    1 = 完全重合
```

**不删的后果**：你会在车牌上画 200 个框，看起来像一坨绿色。

代码骨架（就这么点东西，别怕）：

```python
def nms(boxes, scores, iou_thresh=0.45):
    order = scores.argsort()[::-1]          # 按分数从高到低排序，拿到的是"下标"
    keep = []
    while order.size > 0:
        i = order[0]                        # 当前分数最高的
        keep.append(i)
        if order.size == 1:
            break
        iou = iou_of(boxes[i], boxes[order[1:]])       # 和其余所有框算 IoU
        order = order[1:][iou <= iou_thresh]           # 只留重叠不高的，进下一轮
    return keep
```

**注意**：全部用 NumPy 整体算，**不要写 for 循环遍历 25200 个框**——
正是你 Day 9 学的"向量化思维"。25200 个框如果逐个循环，慢到你会以为程序卡死。

## 5. letterbox：模型要 640×640，但你的图是 1920×1080

### 不能直接拉伸

直接把 1920×1080 拉成 640×640，车牌会被**压扁**（宽高比例变了），
模型见到的车牌和它训练时见到的形状不一样 → 精度崩。

### 正确做法：保持比例缩放 + 灰边填充

```
原图 1920×1080
   ↓  r = 640 / 1920 = 0.3333     （取 min(640/1080, 640/1920)，保证装得下）
缩放到 640×360
   ↓  上下共需要填 640-360 = 280 像素
上下各填 140 像素的灰边（值 = 114，YOLO 的标准灰）
   ↓
得到 640×640
```

```python
def letterbox(img, size=640):
    h, w = img.shape[:2]                      # ← 先高后宽（Day 8 学的）
    r = min(size / h, size / w)
    nh, nw = int(round(h * r)), int(round(w * r))
    resized = cv2.resize(img, (nw, nh))       # ← dsize 先宽后高（Day 11 学的）
    canvas = np.full((size, size, 3), 114, dtype=np.uint8)
    top, left = (size - nh) // 2, (size - nw) // 2
    canvas[top:top+nh, left:left+nw] = resized    # ← 切片赋值（Day 8 学的）
    return canvas, r, left, top
```

### ⭐ 关键一步：把框映射回原图

算出来的框是 **letterbox 坐标系（640×640）** 里的，
不映射回去的话，框会**整体偏移 + 尺寸不对**——这是新手画错框的第一大原因。

```
x_原图 = (x_letterbox - pad_left) / r
y_原图 = (y_letterbox - pad_top ) / r
```

> **90% 的教程会漏讲这一步。** 记住：`letterbox()` 输出 `r, left, top` 三个数，
> 就是为了后面"退货"用的。

## 7. 数据集与标注（M4 的另一半）

### 数量：100–200 张就够

这是**微调**（fine-tune），不是从零训练。模型已经认识"什么是物体"，你只需要教它"车牌长这样"。

### 怎么拍

| 要求 | 原因 |
|---|---|
| 手机拍，越多角度越好 | 只拍正面 → 侧面就检不出来 |
| 光照要杂：白天 / 傍晚 / 地库 / 逆光 | 只在晴天拍 → 晚上全瞎 |
| 距离要远中近都有 | 车牌大小分布要接近真实场景 |
| **故意拍一些失败的**：模糊、遮挡、脏车牌、倾斜 | 让模型知道"这些也算车牌"，否则一模糊就漏检 |
| 一张图里最好有 1–3 个车牌 | 全是单牌 → 多牌场景会漏 |

⚠️ **不要只拍"好认的"**。数据集的难点样本才决定模型上限。

### 标注工具

- **X-AnyLabeling**（推荐，支持自动标注——先用模型预标，你只改错的，快 5 倍）
- labelImg（老牌，简单）

### ⚠️ YOLO 标注格式（和 Day 11 学的完全不同！）

每张图一个**同名 `.txt`**，每行一个目标：

```
0 0.512 0.633 0.180 0.060
↑    ↑     ↑     ↑     ↑
类别 中心x 中心y 宽   高        ← 全部是 0~1 的"归一化"值，不是像素！
```

| | Day 11 学的 | YOLO 标注 |
|---|---|---|
| 表示 | `(x1, y1, x2, y2)` 左上右下 | `(cx, cy, w, h)` 中心 + 宽高 |
| 单位 | **像素** | **归一化 0~1**（除以图宽/图高） |

**换算关系**（你以后要写转换脚本）：
```python
cx = (x1 + x2) / 2 / img_w
cy = (y1 + y2) / 2 / img_h
w  = (x2 - x1) / img_w
h  = (y2 - y1) / img_h
```

## 8. 常见坑（先记住，遇到不慌）

| 坑 | 现象 | 真正原因 |
|---|---|---|
| 框整体偏移 | 所有框都往一个方向偏 | **忘了减 letterbox 的 pad** |
| 框大小不对 | 框比目标小一圈 / 大一圈 | 忘了除以 / 乘以缩放系数 `r` |
| 满屏几百个框 | 一个目标上画了一坨 | **忘了 NMS** |
| 一个框都没有 | 输出空 | 置信度阈值太高；或**该 sigmoid 没 sigmoid**（分数全在 0~1 之外） |
| 框位置对但类别全错 | 框住车却写着"狗" | 类别名字表下标对错了 |
| 框宽高是 0 或巨大 | 全屏一个大框 | 解码公式错（`*2-0.5` 或 `**2` 漏了） |
| 程序慢得像卡死 | 跑一张图几十秒 | **用 for 循环遍历 25200 个框**（要用 NumPy 向量化） |

### 排查顺序（永远这个顺序）

```
① 先打印数字：shape / dtype / min / max / 前几个分数
② 数字不对 → 怀疑 sigmoid、怀疑解码公式
③ 数字对但框不对 → 怀疑 letterbox 映射（pad 和 r）
④ 框对但太多 → NMS
⑤ 全对但慢 → 向量化
```

> **先看数字，再怀疑公式。** 你已经在 `onnx2rknn.py` 里养成这个习惯了，继续保持。

# 附录 A：模型轻量化 —— 该做什么，不该做什么

> 起因：**"想继续深入研究，是不是该考虑官方 YOLO 的轻量化？"**
> 这个问题要拆成两半回答，而且两半的答案**完全相反**。

## A.1 先把"轻量化"这个词拆开

| 说法 | 真实含义 | 该不该做 |
|---|---|---|
| "用轻量化的 YOLO" | 用官方 **nano** 系列（`yolov5n` / `yolov8n`） | ✅ **该做**，而且你已经在做 |
| "自己把模型做轻" | 剪枝、蒸馏、换 backbone、NAS | ❌ **现阶段别做** |

**"选官方的小模型"和"自己动手把模型变小"，是两件完全不同的事。**

---

## A.2 ⭐ 关键纠正：在 NPU 上，"轻量化" ≠ "FLOPs 小"

这是最重要的一句话：

> **在 GPU 上，模型快不快主要看 FLOPs。**
> **在 NPU 上，模型快不快主要看"算子它认不认"。**

RK3588 的 6 TOPS 是**理论峰值**，实际能不能吃到，取决于：

| 真正的瓶颈 | 说明 | 你的模型有没有踩 |
|---|---|---|
| **① 算子支持** | SiLU、Hardswish、Focus、大 kernel、动态 shape 不被 NPU 支持 → **回退到 CPU 跑** → 慢 10 倍以上 | ✅ 已解决（见下） |
| **② 量化位宽** | 只有 **INT8** 能跑满 6 TOPS；FP16 大约只有一半；混合精度更慢 | 待做（你计划里的 INT8） |
| **③ 访存带宽** | 残差、concat 越多 → 中间张量越多 → 带宽压力越大，NPU 算得快但"喂不饱" | 官方模型已优化 |
| **④ 结构规整度** | 不规则的、动态的、自定义的结构 → 转换时各种报错 | ❌ 自己魔改就会踩 |

### 证据就在你手上：`yolov5s_relu.onnx` 里的那个 `relu`

你一直在用的这个模型，名字里的 **`relu` 就是官方做的一次"轻量化"**：

```
原始 yolov5s：激活函数用 SiLU（sigmoid 的变体，NPU 支持差）
      ↓  RKNN 官方动手
yolov5s_relu：激活函数换成 ReLU（NPU 原生支持）
精度        ：几乎不变
NPU 上的速度：快好几倍
```

**这才是"官方轻量化"在 RKNPU 语境下的真实含义**——不是"把参数变少"，
而是"**把模型改成 NPU 爱吃的样子**"。

> **所以你已经无意中用了一次官方轻量化。** 这就是为什么"先跑通官方例程"这么重要——
> 官方已经把 NPU 的坑替你踩过一遍了。

## A.3 那"自己动手轻量化"为什么现阶段别做

不是学术上没价值，而是**性价比极差**：

| 手段 | 学术上 | 在你的项目里 |
|---|---|---|
| **结构化剪枝** | 有效 | 通道数一变，ONNX 要重导，**算子可能变得 RKNN 不支持**；调剪枝比例 + 微调恢复精度，轻松吃掉 1–2 周 |
| **非结构化剪枝**（稀疏化） | 有效 | **NPU 不支持稀疏加速** → 白剪，还更慢 |
| **知识蒸馏** | 有效 | 要先训一个 teacher，CPU 上训练 = 几天，收益通常 < 换模型 |
| **换 backbone**（MobileNet/GhostNet） | 有效 | 改结构 = 重新训练 + 重新踩算子坑，**前面所有工作作废** |
| **NAS** | 有效 | 需要 GPU 集群，和你的项目无关 |

**一句话**：这些手段的收益是"快 20%"，代价是"多花两周 + 很可能转换失败"。

而你现在**连基线都还没建立**——还没跑出"yolov8n 在你的板子上到底多少 FPS"。
**没有基线，就无从判断轻量化有没有用。**

## A.4 ⭐ 但有个更重要的判断：你的瓶颈很可能根本不在 NPU

参考数据（RK3588 **单核**，官方 benchmark）：

| 模型 | 输入 | 精度 | FPS |
|---|---|---|---|
| yolov8n（检测） | 640×640 | INT8 | **73.5** |
| LPRNet（车牌字符） | 24×94 | FP16 | **586.4** |

**检测 73.5 FPS 已经远超实时需求（25–30 FPS）。**

现实里端到端跑不到 73 FPS，但**掉帧的原因通常不在 NPU**，而在：

| 真正的瓶颈 | 优化手段 | 收益 |
|---|---|---|
| 摄像头取帧（USB 带宽 / 驱动） | 降分辨率 / MJPG 格式 / 多线程取帧 | **大** |
| 后处理（NMS、letterbox）用 for 循环 | **NumPy 向量化** | **大** |
| 画框、`imshow`、编码显示 | 减少拷贝、别每帧重新分配内存 | 中 |
| 内存拷贝（CPU↔NPU） | 零拷贝 `rknn_outputs` / DMA buffer | 中 |
| 模型本身 | 换更小的模型 | **小**（因为已经够快） |

> **结论：优化"模型"的收益 < 优化"前后处理和 IO"的收益。**
> 把 NMS 从 for 循环改成 NumPy 向量化，可能比你花两周剪枝还快。

## A.5 推荐的"轻量化"路线（按性价比排序）

### Tier 1 — 必做，成本低、收益高、**能写出结论**

| # | 做什么 | 为什么值 | 成本 |
|---|---|---|---|
| 1 | **INT8 量化 + 校准集质量** | 这是真正的大头（FP16 → INT8 差不多翻倍） | 已在计划里 |
| 2 | **分辨率实测曲线**：640 / 512 / 416 / 320 | 做一张「分辨率 × 精度 × FPS」表。**这是能写进报告的实测量** | 1 天 |
| 3 | **模型选型对比**：yolov5n / yolov6n / yolov8n / yolov10n / yolov11n | 同条件实测，一张表就是复试材料 | 2–3 天 |
| 4 | **前后处理向量化 + 多线程取帧** | 真正决定端到端帧率 | 2–3 天 |

### Tier 2 — 有余力做，能体现"研究"含量

| # | 做什么 | 说明 |
|---|---|---|
| 5 | **量化误差逐层分析** | RKNN-Toolkit2 的 `accuracy_analysis()` 能看**哪一层掉点最多** → 再对该层做**混合量化**（敏感层保 FP16）。这是很漂亮的一段工作 |
| 6 | **粗到精（coarse-to-fine）两级检测** | 小图先粗定位车牌大致区域 → 再对 ROI 高分辨率精检。**特别适合"车牌是小目标"这个特点**，是真算法工作 |
| 7 | **换专用轻量检测器** | NanoDet-Plus / YOLO-Fastest / MobileNetV3-SSD 等，对比它们和 YOLO 在你的场景下的表现 |

### Tier 3 — 研究级，除非要发论文，否则别碰

```
知识蒸馏 / 结构化剪枝 / QAT（量化感知训练）/ NAS
```

**判断标准（很好用）**：
> **能不能用一句话说清"这个改动带来什么收益"，并且"能测出来"？**
> 说不清、测不出的，先不做。

## A.6 一个更激进的思路（但要知道代价）

你的场景如果是**停车场闸机 / 固定摄像头**，车牌位置分布很集中，那么：

| 方案 | 做法 | 收益 | 代价 |
|---|---|---|---|
| 固定 ROI | 摄像头固定 → 车牌基本在画面下 1/3 → **直接裁 ROI 送 LPRNet，不做检测** | 省掉整个检测模型 | 摄像头一动就废 |
| 传统 CV 粗定位 | 颜色（蓝/绿牌）+ 形态学 + 边缘 → 找候选区域 | 极快、零模型 | **鲁棒性差**（光照/角度一变就崩） |
| 检测 + 识别接力 | YOLO 检出框 → 裁剪 → LPRNet | 鲁棒，各有分工 | 要两个模型 |

> **但我要给你一个诚实的建议**：从"复试材料"的角度看，
> **"YOLO + NPU 部署 + 量化调优"的技术含量，明显高于"用颜色阈值找车牌"。**
> 传统 CV 定位是个**工程取巧**，不是加分项。别为了省一点算力把项目显得"low"了。

## A.7 结论：现在该做什么

| 判断 | 动作 |
|---|---|
| ✅ 用官方 nano（`yolov8n`） | 照做，这就是"官方轻量化" |
| ✅ 把 INT8 量化做好 | 这才是"轻量化"的大头，且你已经在计划里 |
| ✅ 建基线：跑出你的 FPS / 精度数字 | **没有基线，一切优化都是瞎猜** |
| ✅ 补一张「分辨率 × 精度 × FPS」实测表 | 成本低，收获可写进报告 |
| ✅ 优化后处理（向量化 NMS）和多线程取帧 | **收益大于模型优化** |
| ❌ 剪枝 / 蒸馏 / 魔改 backbone | 现在做 = 花两周 + 大概率转换失败 |
| 🔶 Tier 2 的量化分析、粗到精两级检测 | 等主线跑通、封版前有余力再做 |

> **一句话**：**"轻量化"在你这个项目里的正确形态，是「INT8 量化 + 官方 nano 选型 + 前后处理优化」，
> 不是「自己剪枝蒸馏」。** 前者一周能做完且有效，后者两周做不完且可能作废。
