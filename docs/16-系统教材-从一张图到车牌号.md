# 第 1 章　图像在计算机里到底是什么

## 1.1 从一个具体的问题开始

你拍了一张照片：**4096 × 3072 像素**，里面有一辆车，车牌上写着 `京A·12345`。

你想让电脑告诉你：**车牌号是什么？**

**先问一个更基础的问题**：这张照片在电脑眼里是什么？

## 1.2 答案：一堆数字

```
一张 4096×3072 的彩色照片
= 4096 × 3072 × 3 = 3774 万个数字
（每个数字 0~255，表示那个点的亮度）
```

用你 Day 8 学的话说：

| 图 | 数组形状 | 含义 |
|---|---|---|
| 灰度图 | `(高, 宽)` | 二维，每格一个数 |
| 彩色图 | `(高, 宽, 3)` | 三维，每格三个数（B/G/R） |

```python
img = cv2.imread("test1.jpg")
img.shape        # (3072, 4096, 3)

img[0, 0]        # 左上角那个像素的三个值，例如 [120, 135, 150]
img[100, 200]    # 第 100 行、第 200 列那个像素
```

> **⚠️ 记住"先高后宽"**：`img[行, 列]` = `img[y, x]`。

## 1.3 关键矛盾

**3774 万个数字里，藏着"车牌在哪、写着什么"这个信息。但人看不过来，程序也"看不懂"数字的意义。**

如果让你写个 `if` 判断——做不到。**因为车牌的位置、大小、光照、角度，每一种情况都不一样。**

## 1.4 所以我们需要什么

> **需要一个"函数"**：输入 3774 万个数字，输出"车牌在哪、是什么"。

这个函数**人写不出来**（规则太多、太复杂）。

**但它可以被"学"出来。**

## 1.5 本章收获

| 概念 | 一句话 |
|---|---|
| 图像 | 一个 NumPy 数组：灰度 `(高,宽)`，彩色 `(高,宽,3)` |
| 图像的索引 | `img[y, x]`，**先高后宽** |
| 核心矛盾 | 数字里有信息，但**没有可写出来的规则**去提取它 |

**→ 下一章的问题**：这个"学出来的函数"到底是什么东西？它长什么样？

# 第 2 章　模型：一个你不需要理解内部的函数

## 2.1 模型 = 一个超大的函数

```
                     ┌─────────────────┐
   3774 万个数字  →  │      模型        │  →  一堆数字
   （一个数组）      └─────────────────┘     （几个数组）
                          ↑
                    内部有 700 万个"旋钮"（参数）
```

- **输入**：一个数组（你的图）
- **输出**：几个数组（一堆数字）
- **参数**：几百万个浮点数，**是训练出来的，不是人写的**

**关键认知**：你**不需要知道内部每个旋钮是干什么的**。就像你不需要知道 `sin()` 是怎么算出来的，也能用它。

## 2.2 训练 vs 推理

| | 训练（training） | **推理（inference）** |
|---|---|---|
| 做什么 | 反复调整那 700 万个旋钮，让输出越来越对 | **把数据喂进去，拿到输出** |
| 需要什么 | 海量标注数据 + GPU + 几天时间 | 只要一台能跑模型的机器 |
| 谁来做 | 大公司 / 研究者 | **你** |

> **你的项目 100% 是"推理"。** 你**不需要训练**——车牌检测和字符识别，官方都有现成的模型。

## 2.3 推理你已经做过一次了

回头看你的 `onnx2rknn.py`：

```python
rknn.load_onnx(...)          # 读模型
rknn.build(...)              # 编译
rknn.init_runtime()          # 初始化
outputs = rknn.inference(data)    # ← 这就是推理：喂数据，拿数字
```

**新东西不是"怎么跑模型"，而是"输出的那些数字是什么意思"。**

## 2.4 "用模型"只需要知道三件事

```
① 输入要什么形状？      ← 例如 (1, 3, 640, 640)
② 输出是什么形状？      ← 例如 (1, 255, 80, 80)
③ 输出的数字怎么解释？  ← 这是最难的一件，第 3~7 章专门讲
```

## 2.5 本章收获

| 概念 | 一句话 |
|---|---|
| 模型 | 一个**从数组到数组**的超大函数，参数是学出来的 |
| 训练 | 调整参数的过程（**你不用做**） |
| **推理** | **喂数据、拿输出**（**你的全部工作**） |
| 用模型的三个问题 | 输入形状 / 输出形状 / **输出怎么解释** |

**→ 下一章的问题**：模型内部到底在干什么？为什么它的输出会是 `(1, 255, 80, 80)` 这么奇怪的形状？

# 第 3 章　卷积：这个函数为什么能"看懂"图

## 3.1 最朴素的想法：看小窗口

人看车牌，不是一次看整张照片，而是**眼睛扫过一个个局部**。

计算机可以模仿这个思路：**用一个小窗口在图上滑动，每次只看窗口里那一小块。**

```
一张图 + 一个 3×3 的小窗口

┌─────────────┐
│ ▓▓▓         │        窗口里的 9 个数
│ ▓▓▓  ← 窗口 │        ×  9 个权重
│ ▓▓▓         │        =  1 个数   ← 这个数表示"这一小块有多像某个特征"
└─────────────┘
```

滑过整张图 → 得到一张**新的图**，每个位置一个数。

**这个操作叫"卷积（convolution）"。** 那个小窗口的 9 个权重，就是模型要学的参数。

## 3.2 一次卷积只能看一种特征

- 一个窗口（一组权重）= 一种特征（比如"有没有竖着的边缘"）
- **多个窗口并行** = 多种特征同时找

**于是就有"通道"这个概念了。**

> **复习一下你已经会的东西**：彩色图 `(高, 宽, 3)` 是 3 张二维图叠起来（B/G/R 各一张）。
>
> **卷积层的输出完全一样的形式**，只是叠的不是颜色，而是**特征图**：
>
> ```
> (高, 宽, 64)   = 64 张二维图叠起来
>                 第 0 张："哪里有竖边缘"
>                 第 1 张："哪里有横边缘"
>                 ...
>                 第 63 张："哪里有某种纹理"
> ```
>
> **"通道"的意思从"颜色"变成了"特征"。**

## 3.3 层数越深，看得越大

```
第 1 层：看 3×3 像素      → 只能看到"边缘、角、点"
第 2~5 层：组合边缘        → "纹理、条纹"
第 10 层左右：组合纹理      → "轮子、车窗、文字块"
最后几层：组合部件          → "整个车牌"、"整辆车"
```

**这就是"深度"学习的来历**——一层层往上抽象。

## 3.4 图越来越小，通道越来越多

每过几层，会做一次**下采样**（把图缩小一半）：

```
输入图        640 × 640 × 3
   ↓ 下采样
             320 × 320 × 32
   ↓
             160 × 160 × 64
   ↓
              80 ×  80 × 128        ← 这里！
   ↓
              40 ×  40 × 256        ← 这里！
   ↓
              20 ×  20 × 512        ← 这里！
```

**为什么要缩小？**
- 图越小，计算量越小
- 感受野越大（每个点"看到"的原图范围更大）

## 3.5 ⭐ 伏笔揭晓：`80×80` 和 `20×20` 是哪来的

对比一下你的模型输出：

```
输出0:  (1, 255, 80, 80)
输出1:  (1, 255, 40, 40)
输出2:  (1, 255, 20, 20)
                  ↑  ↑
              这两个数就是上面下采样的结果！
```

| 输出 | 网格 | 640 ÷ 网格 = **步长 stride** | 负责 |
|---|---|---|---|
| 80×80 | 80 | 640/80 = **8** | 小目标 |
| 40×40 | 40 | 640/40 = **16** | 中目标 |
| 20×20 | 20 | 640/20 = **32** | 大目标 |

**"stride（步长）"的来历就是这个**：网络缩小了 8 倍，所以**特征图上的 1 格 = 原图的 8 个像素**。

> **一个 80×80 的格子代表原图 8×8 像素的区域。**
> 这就是为什么"车牌是小目标"→ 要关注 80×80 这一支：**只有它看得够细。**

**为什么要三个尺度？**
- 8×8 像素的格子"看不住"一辆大巴（视野太小）
- 32×32 像素的格子"看不清"一个小车牌（分辨率太低）
- **三个尺度各管一段，合起来覆盖大中小目标**

## 3.6 那 `255` 呢？

255 就是**那一次卷积输出的通道数**：

```
最后那个卷积层，输出通道数 = 3 × 85 = 255
```

**为什么偏偏是 3 × 85？** —— 这是**人为设计的**，不是网络自己长出来的。设计逻辑在第 4 章。

## 3.7 本章收获

| 概念 | 一句话 |
|---|---|
| **卷积** | 用小窗口在图上滑动，提取局部特征 |
| **通道** | 从"颜色"变成"特征图"，`(高,宽,64)` = 64 张特征图叠起来 |
| **深度** | 层数越深，看到的越抽象（边缘→纹理→部件→物体） |
| **下采样** | 图越来越小、通道越来越多 |
| **网格 / stride** | 特征图 80×80，对应原图的 stride = 8 |
| **三尺度** | 80×80 / 40×40 / 20×20 分别管小 / 中 / 大目标 |

**→ 下一章的问题**：`255 = 3 × 85` 是人为设计的。**为什么这么设计？那 85 个数到底是什么？**

# 第 4 章　检测问题怎么定义

## 4.1 目标检测要输出什么

```
输入：一张图
输出：若干个框，每个框带一个类别
      ┌─────────┐
      │  车 0.95│
      └─────────┘
```

## 4.2 难点：框是"任意"的

一个框需要 4 个数（中心 x,y + 宽高）。问题是：

- 框可以出现在**任何位置**
- 可以是**任何大小**
- 可以有**任意多个**

**让模型直接"回归"这 4 个数，太难学了。** 因为模型不知道"该往哪个方向猜"。

## 4.3 ⭐ YOLO 的核心思想：把图切成格子

> **不要让模型"凭空猜框"，而是：把图切成 80×80 个格子，每个格子负责预测"落在它里面的物体"。**

```
640×640 的图，切成 80×80 个格子

┌─┬─┬─┬─┬─┐
├─┼─┼─┼─┼─┤    每个格子 8×8 像素
├─┼─┼─┼─┼─┤    每个格子独立回答：
└─┴─┴─┴─┴─┘    "我这里面有东西吗？在哪？多大？是什么？"
```

**好处**：
- 每个格子只关心**自己那一小块**，问题变简单了
- 物体中心落在哪个格子，就由哪个格子负责（**责任明确**）
- 可以**完全并行**（80×80 = 6400 个格子同时算，GPU/NPU 最喜欢这种）

## 4.4 为什么还要"预设框"（anchor）

即使切成格子，还是有个问题：**同一个格子里，物体可能很宽（车）也可能很高（人）。**

如果让模型从零猜"框有多宽多高"，依然很难。

> **解法：给每个格子预设 3 种框形状，让模型只说"哪个最接近、还要改多少"。**

```
每个格子配 3 个"先验框"（anchor）：

  anchor 0        anchor 1        anchor 2
  ┌────┐          ┌──┐            ┌──────┐
  │    │          │  │            │      │
  └────┘          │  │            └──────┘
   扁宽            瘦高             更扁宽
  (10×13)         (16×30)         (33×23)
```

**这 3 个尺寸是人为设定的**（YOLOv5s 官方的值），代表"常见物体的典型形状"。

> **类比**：买衣服时，你不会让裁缝"从零做一件"，而是说"我要 M 码，袖子再长 2 厘米"。
> **anchor 就是那个"M 码"。**

**这就是 YOLO 的核心设计思想**，也是那句"**模型学的不是框在哪，而是相对周围格子偏多少**"的来历。

## 4.5 于是 85 个数定下来了

```
每个 anchor 要回答 5 件事 + 判断 80 个类别：

┌────┬────┬────┬────┬─────┬─────────────────────────────┐
│ cx │ cy │ w  │ h  │ obj │   80 个类别的分数            │
└────┴────┴────┴────┴─────┴─────────────────────────────┘
  ↑              ↑     ↑            ↑
 框在哪          框多大 有没有东西   是什么
（相对格子的微调量）
```

```
一个格子的通道数 = 3 个 anchor × 85 = 255      ← 伏笔揭晓！
```

## 4.6 完整的总账

```
80×80 尺度：80×80×3 = 19200 个候选框
40×40 尺度：40×40×3 =  4800 个候选框
20×20 尺度：20×20×3 =  1200 个候选框
─────────────────────────────────────
合计               = 25200 个候选框
```

**模型的输出，就是"25200 个候选框的原始参数"。后处理的全部工作，就是在这 25200 个里挑出真正的框。**

## 4.7 本章收获

| 概念 | 一句话 |
|---|---|
| **网格 grid** | 把图切成 80×80 格，每格独立预测，责任明确 |
| **锚框 anchor** | 预设的 3 种框形状，模型只学"微调量"，不学"框多大" |
| **85 个数** | `cx, cy, w, h, obj` + 80 个类别分 |
| **255** | `3 anchor × 85` |

**→ 下一章的问题**：那 5 个数（`cx,cy,w,h,obj`）是"微调量"，**具体怎么算成图上的真实坐标？**

# 第 5 章　解码：把 255 个数字翻译成一个框

## 5.1 先看清楚"一个格子"长什么样

```python
o = outs[0][0].reshape(3, 85, 80, 80)
#                 ↑  ↑   ↑   ↑
#              anchor 通道 行  列
```

用四层地址读它：`o[anchor, 通道, 行, 列]`

| 通道 | 含义 | 范围 |
|---|---|---|
| 0 | `tx` 框中心的**横向偏移** | 0~1（已 sigmoid） |
| 1 | `ty` 框中心的**纵向偏移** | 0~1 |
| 2 | `tw` 框的**宽度系数** | 0~1 |
| 3 | `th` 框的**高度系数** | 0~1 |
| 4 | `obj` **有没有东西** | 0~1 |
| 5~84 | 80 个**类别分数** | 0~1（softmax） |

> **为什么是 0~1？** 因为模型最后做了 `sigmoid`——把任意实数压到 0~1，才能当"比例"用。

## 5.2 解码公式，逐项拆解

```python
cx = (tx * 2 - 0.5 + grid_x) * stride
cy = (ty * 2 - 0.5 + grid_y) * stride
w  = (tw * 2) ** 2 * anchor_w
h  = (th * 2) ** 2 * anchor_h
```

### `cx` 那行：四步

| 步骤 | 表达式 | 在干什么 |
|---|---|---|
| ① | `tx * 2` | 0~1 → **0~2** |
| ② | `- 0.5` | 0~2 → **-0.5~1.5**。**允许框中心跑出格子一点**（否则相邻格子的框永远接不上） |
| ③ | `+ grid_x` | 格子内偏移 → **整张图上的格子坐标**（第 17 列 + 偏 0.5 = 17.5） |
| ④ | `* stride` | 格子单位 → **像素单位**（1 格 = 32 像素） |

### `w` 那行：三步

| 步骤 | 表达式 | 在干什么 |
|---|---|---|
| ① | `tw * 2` | 0~1 → 0~2 |
| ② | `** 2` | **平方**：保证为正；同时放大差异（0.5→0.25，1.5→2.25） |
| ③ | `* anchor_w` | **乘上预设框宽度**——这就是 anchor 的意义（"M 码 × 1.2 倍"） |

所以 `w` 的范围是 `0 ~ 4 × anchor_w`。

## 5.3 ⭐ 完整算例（用你项目里的真实数字）

**场景**：找那个行人。它在
```
尺度2（20×20 网格，stride = 32），anchor 1，格子（第 14 行，第 17 列）
```

**模型给出的 5 个数**（你亲手跑出来的）：

```
tx = 0.83987457
ty = 0.43791735
tw = 0.26639083
th = 0.39335190
obj = 0.86260350
```

**已知**：`stride=32`、`anchor_w=156`、`anchor_h=198`、`grid_x=17`、`grid_y=14`

### 算 `cx`

```
① tx × 2      = 0.83987457 × 2    = 1.67974914
② − 0.5       = 1.67974914 − 0.5  = 1.17974914
③ + grid_x    = 1.17974914 + 17   = 18.17974914
④ × stride    = 18.17974914 × 32  = 581.75

→ cx = 581.75
```

**读一下**：581.75 像素，在 640 宽的图里靠右（91%）。**和原图里行人在右侧（87%）对得上。** ✓

### 算 `cy`

```
① 0.43791735 × 2 = 0.87583470
② − 0.5          = 0.37583470
③ + 14           = 14.37583470
④ × 32           = 460.03

→ cy = 460.03
```

### 算 `w`

```
① 0.26639083 × 2 = 0.53278166
② ** 2           = 0.28385630
③ × 156          = 44.28

→ w = 44.28
```

### 算 `h`

```
① 0.39335190 × 2 = 0.78670380
② ** 2           = 0.61890280
③ × 198          = 122.54

→ h = 122.54
```

### 转成左上-右下

```
x1 = cx − w/2 = 581.75 − 22.14 = 559.61
y1 = cy − h/2 = 460.03 − 61.27 = 398.76
x2 = cx + w/2 = 581.75 + 22.14 = 603.89
y2 = cy + h/2 = 460.03 + 61.27 = 521.30
```

**得到的框**：`(559.6, 398.8) - (603.9, 521.3)`（letterbox 640×640 坐标）

### 对照程序输出

```
person 0.9987   (560,399)-(604,521)
                 ↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑↑
                 手算结果分毫不差 ✓
```

> **这就是"解码"的全部内容。** 你手算的这四步，就是程序内部对 25200 个候选框做的事情。

## 5.4 本章收获

| 概念 | 一句话 |
|---|---|
| **解码 decode** | 把"相对格子的微调量"算成"图上的像素坐标" |
| `tx*2-0.5` | 允许框中心跑出格子（范围 -0.5~1.5） |
| `+ grid` | 从格子内偏移变成图上的格子坐标 |
| `* stride` | 从格子单位换成像素单位 |
| `(tw*2)**2` | 保证宽高为正 + 放大差异 |
| `* anchor` | 在预设形状基础上做缩放 |

# 第 6 章　挑框：置信度与 NMS

## 6.1 两个分数，一个结论

每个候选框身上有两个"分数"：

| 名称 | 通道 | 回答什么 |
|---|---|---|
| **obj** | 4 | "**这个格子里有东西吗**" |
| **类别分数** | 5~84 | "**如果有，是什么**" |

**最终置信度 = obj × 类别分数**

### 为什么要相乘

因为两个条件必须**同时**成立（这就是 Day 2 学的 `and` 逻辑）：

| obj | 类别分 | 模型的潜台词 | 处理 |
|---|---|---|---|
| 0.90 | 0.95 "车" | 有东西，而且是车 | ✅ 保留 |
| 0.90 | 0.01 "车" | 有东西，但我不知道是啥 | ❌ 丢弃 |
| 0.01 | 0.95 "车" | 自相矛盾（说有车，又说这格空的） | ❌ 丢弃 |

> **obj 的真正作用**：模型给出 25200 个候选，其中**绝大多数落在天空、路面、墙上**。
> **obj 就是用来干掉这些背景垃圾的。**

**你项目里的实测**：
```
不用 obj ：  2094 个候选通过阈值  →  NMS 后 402 个框（满是误检）
用 obj   ：    44 个候选通过阈值  →  NMS 后   3 个框 ✓
```

### 关于 sigmoid 和 softmax

| | 作用 | 判断方法 |
|---|---|---|
| **sigmoid** | 每个数独立压到 0~1，**可以多个同时高** | 一组数加起来**不等于** 1 |
| **softmax** | 一组数**加起来等于 1**（互斥） | `sum()` ≈ 1 |

**你这个模型的类分支是 softmax**（实测 80 个类分数之和 = 1.0047）。
**后果**：背景格子也一定有个"赢家"，分数不会整体很低 → **阈值要选得比 sigmoid 时更高**。

## 6.2 阈值过滤

```python
keep = (conf > 0.5)
```

一步就能从几千个候选里砍掉大部分。

**阈值怎么选**：跑一遍不同值，看框数的变化曲线。

```
阈值 0.25 → 350 个      正常的图应该出现"平台 + 悬崖"：
阈值 0.55 →  21 个        0.9 → 3 个    ← 平台（真物体）
阈值 0.70 →   2 个        0.8 → 3 个
                          0.4 → 200 个  ← 悬崖（背景涌进来）
```

## 6.3 还剩一个问题：一个目标周围有几百个框

**同一个车牌周围会冒出几百个候选框，它们说的其实是同一件事。**

因为相邻格子、相邻 anchor 都会"瞄上"同一个物体。

## 6.4 IoU：两个框重叠多少

**IoU = 交并比 = 交集面积 ÷ 并集面积**

```
   ┌────────┐
   │  A ┌───┼────┐        交集 = 中间那块
   │    │███│    │        并集 = A + B − 交集
   └────┼───┘    │
        └────────┘
                        IoU = 0  完全不相干
                        IoU = 1  完全重合
```

```python
inter = max(0, xx2-xx1) * max(0, yy2-yy1)
iou = inter / (area_A + area_B - inter)
```

## 6.5 NMS：非极大值抑制

**思想**：谁的分数最高就信谁，把和它重叠太多的全删掉。

```
① 所有框按置信度从高到低排序
② 取第 1 名 → 定为结果
③ 和它 IoU > 0.45 的（重叠太多的）全部删掉     ← 一次删掉几百个
④ 回到 ②，重复，直到没有框剩下
```

**代码的骨架长这样**：

```python
order = scores.argsort()[::-1]        # 排序
while order.size > 0:
    i = order[0]
    keep.append(i)                    # 第 1 名留下
    iou = iou_of(boxes[i], boxes[order[1:]])   # 和剩下所有框算 IoU
    order = order[1:][iou <= 0.45]             # 只留重叠不高的
```

> **⚠️ 必须用 NumPy 向量化**：`iou_of` 里一次算完"它和剩下所有框"的 IoU。
> 如果写成两层 for 循环遍历几千个框，会慢到你以为程序卡死。
> **这正是 Day 9 学的"向量化思维"。**

## 6.6 本章收获

| 概念 | 一句话 |
|---|---|
| **obj** | "这格有没有东西"，用来干掉背景垃圾 |
| **置信度** | `obj × 类别分数`，两个都要高 |
| **sigmoid vs softmax** | 独立 vs 互斥（`sum()` 是否等于 1） |
| **阈值** | 卡掉低分候选；softmax 时阈值要更高 |
| **IoU** | 两个框的重叠程度 = 交集 ÷ 并集 |
| **NMS** | 按分数排序，保留最高的，删掉重叠 > 阈值的，重复 |

**这两个坐标系对不上。为什么？怎么换算？**

# 第 7 章　坐标回家：letterbox 与反向映射

## 7.1 问题从哪来

模型**只吃 640×640 的输入**（训练时就这么定的）。

可你的照片是 **4096×3072**。

## 7.2 错误做法：直接拉伸

```
4096×3072  →  硬拉成 640×640
```

**后果**：宽高比例从 `4:3` 变成 `1:1` —— **车牌被压扁了**。

模型见到的车牌形状和它训练时见到的**不一样**，精度直接崩。

## 7.3 正确做法：letterbox（信箱模式）

**保持比例缩放 + 空白处填灰边。**

```
原图 4096×3072
   ↓  r = min(640/3072, 640/4096) = 0.15625     ← 取小的，保证装得下
缩放到 640×480
   ↓  高度还差 640-480 = 160 像素
上下各填 80 像素的灰边（值 = 114，YOLO 的标准灰）
   ↓
得到 640×640
```

```python
def letterbox(img, size=640):
    h, w = img.shape[:2]                    # 先高后宽
    r = min(size/h, size/w)
    nh, nw = int(round(h*r)), int(round(w*r))
    resized = cv2.resize(img, (nw, nh))     # dsize 先宽后高
    canvas = np.full((size, size, 3), 114, dtype=np.uint8)
    top, left = (size-nh)//2, (size-nw)//2
    canvas[top:top+nh, left:left+nw] = resized
    return canvas, r, left, top             # ★ 这三个数后面要用
```

**你那次的实测**：`r = 0.1562`，`左填充 = 0`，`上填充 = 80`。

## 7.4 ⭐ 关键一步：反向映射

**解码算出来的框，是在 640×640 的 letterbox 坐标系里的。必须换算回原图。**

```python
x_原图 = (x_letterbox - pad_left) / r
y_原图 = (y_letterbox - pad_top ) / r
```

**为什么要减 pad**：因为上面/左边填了灰边，那些像素在原图里**不存在**。
**为什么要除以 r**：因为缩放时乘过 r。

### 用你的数字验证

```
r = 0.1562，pad_left = 0，pad_top = 80
框（letterbox）： (559.61, 398.76) - (603.89, 521.30)

x1_原图 = 559.61 / 0.1562            = 3582.6
y1_原图 = (398.76 - 80) / 0.1562     = 2040.7
x2_原图 = 603.89 / 0.1562            = 3866.2
y2_原图 = (521.30 - 80) / 0.1562     = 2825.2
```

**程序输出**：`(3582, 2040) - (3865, 2825)` ✓ **对上了**

> ⚠️ **90% 的教程会漏讲这一步**，而它是新手"框画错位置"的**第一大原因**。
> 记住：`letterbox()` 输出 `r, left, top` 三个数，就是为了后面"退货"用的。

## 7.5 一个有用的工程技巧：内容区过滤

框的**中心**必须落在内容区（不是灰边）里：

```python
inside = ((cx >= pad_left) & (cx <= pad_left + cw) &
          (cy >= pad_top)  & (cy <= pad_top  + ch))
```

灰边里不可能有目标，落在那儿的框全是噪声。**这一步没有教科书讲，但效果立竿见影。**

## 7.6 本章收获

| 概念 | 一句话 |
|---|---|
| **为什么要 letterbox** | 硬拉伸会改变宽高比，模型认不出被压扁的车牌 |
| **letterbox** | 保比例缩放 + 灰边填充，并**记住 `r / pad_left / pad_top`** |
| **反向映射** | `(x − pad) / r`，把 letterbox 坐标还原成原图坐标 |
| **内容区过滤** | 框中心必须落在真正有画面的区域里 |

**板子上有 NPU，怎么让模型在 NPU 上跑？**

# 第 8 章　模型怎么变成硬件能跑的东西

## 8.1 一个 N × M 的问题

```
框架有 N 种：  PyTorch / TensorFlow / PaddlePaddle / Caffe ...
硬件有 M 种：  x86 CPU / ARM CPU / 瑞芯微 NPU / 英伟达 GPU / 华为昇腾 ...

如果两两直连 → 需要 N × M 个转换器 → 爆炸
中间加一个统一格式 → 只需要 N + M 个   → 可行
```

**这个统一格式就是 ONNX。**

## 8.2 模型的一生

```
① 训练
   PyTorch → .pt / .pth
                ↓ 导出
② ONNX  (.onnx)          通用交换格式
      · 谁都能读，但谁都不能直接跑
      · 99.9% 的体积是权重浮点数（FP32）
                ↓ RKNN-Toolkit2（在 PC 上转换）
③ RKNN  (.rknn)          瑞芯微私有格式
      · 已经为这颗 NPU "编译"好的产物
      · 绑定芯片型号（rk3588 的不能给 rk3566 用）
      · 权重通常是 INT8
                ↓ 拷到板子
④ librknnrt / lite2      板端运行时
      · 真正指挥 NPU 执行
```

## 8.3 为什么不能直接把 ONNX 丢给 NPU

因为 **NPU 不是 CPU**：

| | CPU | NPU |
|---|---|---|
| 会执行什么 | 通用指令 | **只有硬件里固化的那些算子** |
| 灵活度 | 什么都能算 | **不认识的算子就算不了** |
| 效率 | 通用但慢 | 专用但极快（RK3588 = 6 TOPS） |

**"算子（operator）"就是模型的基本运算单元**（卷积、加法、激活函数…）。
NPU 只认它电路里有的那些——**这就是"算子不支持"报错的来源**。

> **一个真实例子**：原始 YOLOv5 用 `SiLU` 激活函数，NPU 支持很差。
> 官方做了个 `yolov5s_relu`——**把 SiLU 换成 ReLU**，精度几乎不变，NPU 上快好几倍。
> **这就是"官方轻量化"在 RKNPU 语境下的真实含义。**

## 8.4 量化：浮点 → 整数

```
FP32（4 字节）  →  INT8（1 字节）

yolov5s：  约 29 MB  →  约 7 MB
速度：     约 1×     →  约 2×（NPU 只有 INT8 能跑满峰值）
精度：     掉 0.5% ~ 2%（取决于校准集质量）
```

**校准集**：量化需要一些真实图片来"统计数值分布"，通常 100~500 张。
**用真实场景的图**，不要随便凑——校准集选得不好，精度能掉 5% 以上。

## 8.5 版本对齐（一个必踩的坑）

```
RKNN-Toolkit2 (PC)  =  librknnrt (板)  =  rknn_toolkit_lite2 (板)
      都是 2.3.0            都是 2.3.0          都是 2.3.0

rknpu 内核驱动 → 另一套编号（0.9.6），不用对齐
```

**不一致会怎样**：报各种莫名其妙的错（模型版本不匹配、无法加载）。

## 8.6 本章收获

| 概念 | 一句话 |
|---|---|
| **ONNX** | 通用交换格式（AI 界的 Gerber），谁都能读、都不能直接跑 |
| **RKNN** | 瑞芯微私有格式，为 NPU 编译好的产物，**绑定芯片** |
| **算子** | 模型的基本运算单元；**NPU 只认它硬件里有的** |
| **量化** | FP32 → INT8，体积 1/4、速度翻倍、精度掉 1% 左右 |
| **校准集** | 量化统计用的真实图片，**质量决定掉点多少** |
| **版本对齐** | Toolkit2 = librknnrt = lite2 |

**→ 下一章的问题**：`.rknn` 文件有了。**谁在板子上执行它？CPU 和 NPU 到底差在哪？**

# 第 9 章　谁在执行模型

## 9.1 两台机器的分工（背下这张表）

| | **PC（开发机）** | **板子（RK3588）** |
|---|---|---|
| 装什么 | **RKNN-Toolkit2** | `librknnrt` + `rknn_toolkit_lite2` + 驱动 |
| 干什么 | **转换**模型 + **仿真**验证 | **真机推理** |
| 输入 | `.onnx` / `.pt` | `.rknn` |
| 有 NPU 吗 | ❌ 没有 | ✅ 有 |

**关键**：**Toolkit2 是"编译器"，不是"运行时"**——所以板子上不装它。
（就像你不会在 STM32 上装 gcc。）

## 9.2 运行时的分层

```
你的 Python 代码
      ↓  调用
rknn_toolkit_lite2        ← Python API（板端）
      ↓  调用
librknnrt.so              ← C 运行时库（真正指挥 NPU）
      ↓  通过内核接口
rknpu 内核驱动
      ↓
NPU 硬件
```

## 9.3 CPU 和 NPU 的本质区别

| | CPU | NPU |
|---|---|---|
| 核心数 | 4~16 个 | **成百上千个小计算单元** |
| 擅长 | 复杂逻辑、分支跳转 | **简单运算 × 海量并行** |
| 神经网络 | 能跑，但慢 | **为它定制的** |
| 精度支持 | 什么都有 | **主要 INT8** |

**卷积网络的计算特点**：大量"乘加"、几乎没有分支 → **完美契合 NPU**。

**参考性能（RK3588 单核，官方数据）**：

| 模型 | 精度 | FPS |
|---|---|---|
| yolov8n（检测） | INT8 | **73.5** |
| LPRNet（车牌字符） | FP16 | **586.4** |

## 9.4 仿真 vs 真机

```python
# 仿真（PC 上，没有 NPU，慢，但能验证"流程对不对"）
rknn.load_onnx("xxx.onnx")
rknn.build(...)
rknn.init_runtime()              # 不传 target
outputs = rknn.inference(data)

# 真机（板子上）
rknn.load_rknn("xxx.rknn")
rknn.init_runtime(target="rk3588")   # 或者直接在板子上用 lite2
```

> **你踩过的坑**：`.rknn` **不能在 PC 上仿真推理**——
> `E init_runtime: RKNN model that loaded by 'load_rknn' not support inference on the simulator`
> 因为 `.rknn` 是给 NPU 的指令，PC 上没 NPU，解释不了。

## 9.5 本章收获

| 概念 | 一句话 |
|---|---|
| **PC vs 板子** | PC 转换 + 仿真；板子真机推理 |
| **Toolkit2 vs lite2** | 编译器 vs 运行时 |
| **CPU vs NPU** | 通用 vs 专用；NPU 擅长"海量并行 + INT8" |
| **仿真** | PC 上假装有 NPU，只验证流程，速度不代表真机 |

# 附录　术语表（一句话版）

## 图像与数组

| 术语 | 一句话 |
|---|---|
| **通道** | 叠起来的若干张二维图。图片里是 B/G/R，特征图里是各种特征 |
| **shape** | 数组形状。图像是 `(高,宽,通道)` |
| **HWC / CHW** | 两种维度顺序。OpenCV 给 HWC，模型要 CHW |
| **归一化** | 像素 0~255 除以 255 变成 0~1 |

## 模型

| 术语 | 一句话 |
|---|---|
| **模型** | 从数组到数组的超大函数 |
| **参数** | 模型内部几百万个"旋钮"，训练出来的 |
| **训练 / 推理** | 调旋钮 / 用函数。**你的项目只用推理** |
| **卷积** | 小窗口滑动提取局部特征 |
| **算子** | 基本运算单元；NPU 只认它硬件里有的 |
| **下采样** | 图缩小一半，通道翻倍 |
| **感受野** | 一个点"看到"的原图范围 |

## 检测

| 术语 | 一句话 |
|---|---|
| **网格 grid** | 把图切成 80×80 格，每格独立预测 |
| **锚框 anchor** | 预设的框形状，模型只学微调量 |
| **步长 stride** | 特征图 1 格 = 原图多少像素 |
| **解码 decode** | 把微调量算成绝对坐标 |
| **obj** | "这格有没有东西"，用来干掉背景 |
| **置信度** | `obj × 类别分数` |
| **sigmoid** | 压到 0~1，各数独立 |
| **softmax** | 一组数加起来等于 1，互斥 |
| **IoU** | 两框重叠程度 = 交集 ÷ 并集 |
| **NMS** | 一个目标只留最自信的一个框 |
| **letterbox** | 保比例缩放 + 灰边填充 |
| **反向映射** | `(x − pad) / r`，坐标回到原图 |

## 格式与部署

| 术语 | 一句话 |
|---|---|
| **PyTorch / .pt** | 训练框架和它的模型文件 |
| **ONNX** | 通用交换格式，谁都能读、都不能直接跑 |
| **RKNN** | 瑞芯微私有格式，为 NPU 编译好的产物 |
| **RKNN-Toolkit2** | PC 上的编译器（+ 模拟器） |
| **librknnrt** | 板端运行时，真正指挥 NPU |
| **量化** | FP32 → INT8，体积 1/4、速度翻倍 |
| **校准集** | 量化统计用的真实图片 |
| **NPU** | 神经网络专用处理器，擅长海量并行 + INT8 |

# 一页总结

```
一张照片（3774 万个数字）
      ↓  模型是一个"学出来的函数"
   推理
      ↓  输出 25200 个候选框的原始参数（3 个尺度、255 个通道）
   解码          第 5 章
      ↓  变成 25200 个真实坐标的框
   置信度 + NMS  第 6 章
      ↓  变成 3 个框
   反向映射       第 7 章
      ↓  框回到原图坐标系
   画框
      ↓
   【车牌在哪】

   然后裁剪 → 送 LPRNet → 【车牌号是什么】

   最后：ONNX → RKNN → NPU    第 8、9 章
```

> **每一个概念都是为下一个问题服务的。**
> 你不需要记住所有细节，但要记住**这条链的顺序**——
> 卡住的时候，顺着链条往回找，就知道问题出在哪一环。
