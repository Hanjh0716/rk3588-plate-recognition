# 毕业设计选题评估：RK3588 车牌识别 + 上位机 + STM32 云台跟踪

> 评估对象：
> **① RK3588 车牌识别　② 上位机数据传输　③ 基于 STM32 FreeRTOS 的云台跟踪**
>
> 结论先说：**框架很好，选题档次够，但必须做 3 处调整**——
> 重新定义"跟踪"的叙事、把上位机赶出控制闭环、功能分三层可裁剪。

---

## 一、结论速览

| 维度 | 评价 | 说明 |
|---|---|---|
| 选题档次 | ⭐⭐⭐⭐ | 边缘 AI + 实时控制，远超"基于单片机的温湿度采集" |
| 技能匹配 | ⭐⭐⭐⭐⭐ | **正好把你全部技能栈用上**（见 §二.2） |
| 可演示性 | ⭐⭐⭐⭐⭐ | **云台会动**——答辩现场有视觉冲击 |

## 二、为什么这是个好题目

### 1. 它是一个**闭环系统**，不是三个模块拼盘

```
        感知                 决策/通信              执行
   ┌─────────────┐      ┌──────────────┐     ┌─────────────┐
   │  RK3588     │      │  串口协议     │     │  STM32      │
   │  NPU 车牌   │ ───→ │  数据帧       │ ──→ │  FreeRTOS   │
   │  检测+识别  │      │  CRC 校验     │     │  PID → 云台 │
   └─────────────┘      └──────────────┘     └─────────────┘
          ↑                                          │
          └────────── 视觉反馈（闭环）────────────────┘
```

**"感知→通信→控制"构成闭环**——这是评委最想看到的结构。
绝大多数本科毕设是"三个功能各自的 demo"，而闭环意味着**有系统级设计**。

### 2. ⭐ 它正好把你**全部技能栈**都用上

| 你的积累 | 在这个题目里的位置 |
|---|---|
| STM32 / FreeRTOS（老本行，最扎实） | **云台控制的实时任务设计 → 你答辩的主场** |
| 嵌入式 C | 串口协议、驱动、PID |
| **PCB 设计** | **可以自制一块云台驱动板 → 实物加分项**（见 §七） |
| 硬件调试 / 示波器 / 逻辑分析仪 | 通信链路调试、延迟测量 |
| RKNN / NPU 部署（今年新学的） | 车牌检测 + 识别 |
| Python / OpenCV | 前后处理、指标统计、可视化 |

**这一点极其重要**：很多人做毕设会"扔掉一半的积累"——比如纯做 AI 的人不会碰硬件。
你的题目让**新旧技能同时出现在答辩 PPT 上**，而且**你最强的那块（FreeRTOS 实时控制）正好是答辩时最能讲深的地方**。

> **战略**：**让你最扎实的地方成为答辩的主场。**
> 评委问 AI，你可能只能讲个大概；评委问 FreeRTOS 任务划分、优先级反转、PID 抗积分饱和——
> **你能讲得比很多研究生深。这就是你的护城河。**

### 3. 有物理输出，能演、能拍视频、能现场演示

纯软件/纯算法的毕设，答辩只能放日志和曲线图。
**这个能现场动起来**：拿一张车牌照片 → 云台"咔"地转过去对准 → 屏幕上出车牌号。

**视觉冲击 = 印象分。** 而且视频可以放进复试材料里。

### 4. 技术含量确实够

涉及：**NPU 部署与模型量化、串口/CAN 通信协议设计、FreeRTOS 多任务/队列/优先级、PID 闭环控制、坐标映射（像素→角度）、视觉伺服**。

这些随便挑两个都够一个本科毕设。

## 三、⚠️ 最大的问题：重新定义"云台跟踪"的叙事

### 问题所在

**"用云台跟踪**车牌**"这个说法，答辩时会被一句话问倒**：

> 老师："车牌识别是**静态或低速**的场景，识别一次就够了，**为什么要跟踪？**"

而且技术上也不成立：

| 为什么不能"跟踪车牌" | 说明 |
|---|---|
| 车牌是**极小目标** | 检测框抖动大 → 控制误差被噪声主导 → **云台会一直抖** |
| 车牌识别是**事件触发**式 | 识别一次 20ms 就完事，不需要连续跟随 |
| 运动模糊 | 目标一动，车牌就糊，识别率直接崩 |

### ❌ 不要这么写

```
"云台跟踪行驶中的车辆并识别车牌"
"云台实时跟踪车牌位置"
```

### ✅ 换成这个叙事：**视觉伺服（Visual Servoing）**

> **基于视觉伺服的云台主动对准车牌识别系统**
>
> 用识别结果（**车牌框中心与画面中心的偏差**）作为控制误差，
> 驱动二自由度云台，使车牌始终处于画面中心的最佳识别区域，
> **从而在车牌偏离视场、角度倾斜时仍能稳定识别**，
> 实现比固定摄像头**更高的识别率**和**更大的有效监控范围**。

**"视觉伺服"是控制领域有头有脸的经典课题**——用图像误差驱动执行器。答辩时说出来就有分量，而且：

| 优点 | 说明 |
|---|---|
| 技术上自洽 | 云台是**为了对准**，不是为了"追动的东西" |
| **能量化** | 对比「固定摄像头识别率」vs「云台主动对准识别率」→ **画一条曲线**（见 §八） |
| 学术名词正当 | 视觉伺服 / 主动视觉 / PTZ 自动对准 |

### ⭐ 更高级的设计：由粗到精的**两级视觉伺服**

这是能显著提高技术含量的一个点：

```
第一级：跟踪【车/车头】（大目标，好跟）
   · 范围大、速度快、精度要求低
   · 目的：把车"框"到视野中心
        ↓  车辆减速/停稳
第二级：对准【车牌】（小目标，精细）
   · 范围小、速度慢、精度要求高
   · 目的：让车牌正对镜头、位于画面中心
```

**为什么要分层**：大目标检测稳定、跟踪平滑；小目标精度高但抖。
**分层之后，两个矛盾的需求同时被满足。**

> 这和前面章节讲的 **coarse-to-fine（粗到精）检测** 是同一个思想——
> 也说明"车牌是小目标"这个特点**贯穿了你整个项目**。

### 其他站得住的叙事（备选）

| 叙事 | 说明 | 评价 |
|---|---|---|
| **A. 主动对准提高识别率**（推荐） | 见上，可量化 | ⭐⭐⭐⭐⭐ |
| **B. 巡逻扫描 + 锁定识别** | 云台在大范围里巡扫，发现车牌就停下识别 → **扩大监控范围** | ⭐⭐⭐⭐ |
| **C. 多车位巡检** | 轮流对准几个车位，逐一识别 | ⭐⭐⭐ |
| **D. 进场引导** | 锁定来车，引导到最优识别位 | ⭐⭐⭐ |

**建议**：**A 为主叙事 + B 作为"应用场景"**。论文里 A 是技术贡献，B 是应用价值。

## 四、⚠️ 第二个问题：上位机必须"赶出控制闭环"

### 这是控制系统设计的基本原则

```
❌ 错误架构（很多学生会这么做）
RK3588 ──→ 上位机(PC) ──→ STM32 ──→ 云台
              ↑
     问题：控制回路多了 PC 一跳
     · 延迟 +50~200 ms（云台会明显滞后、画圈）
     · PC 卡顿 / 弹窗 / 断网 → 整个系统废掉
     · 违背"控制回路必须实时、可靠"的基本原则
```

```
✅ 正确架构
RK3588 ──串口(115200/921600)──→ STM32 ──→ 云台      ← 控制闭环（低延迟、可靠）
   │
   └──网口/WiFi──→ 上位机                            ← 只在环路外
                   （监控、存储、展示、白名单管理）
```

**关键**：**上位机不在环路里**——它挂了，识别和云台照样工作。

> 这一点**在答辩上讲出来会很加分**：说明你懂"**实时性**"和"**系统可靠性**"，
> 而不是"能跑就行"。这是嵌入式系统设计和"写代码"的区别。

### 上位机该干什么（重新定位）

| ❌ 别做 | ✅ 该做 |
|---|---|
| 中间转发数据（在闭环里） | **数据记录**（车牌、时间、置信度 → CSV/SQLite） |
| 完整桌面软件（Qt/C# 大工程） | **实时看板**（当前车牌、帧率、延迟曲线） |
| 复杂的界面美化 | **白名单管理**（哪些车牌放行） |
| 用户权限系统 | **报警/联动**（识别到 → 通知 / 触发闸门） |

**技术选型建议**：**Python + FastAPI/Flask + 一个网页看板**（用浏览器看，不用写客户端）。
或者最简单的 Qt 单窗口。**1–2 周能做完，不要花 1–2 个月。**

## 五、功能分层：让它"可裁剪"（降风险的核心手段）

**三个模块各自都是一个完整毕设的工作量。** 所以必须分层，保证"砍掉上层也仍是完整毕设"。

| 层级 | 内容 | 预估 | 砍掉的后果 |
|---|---|---|---|
| **必做（核心）** | ① RK3588 车牌检测 + 识别<br>② 串口通信协议（帧头/长度/CRC）<br>③ STM32 FreeRTOS 云台控制 + PID<br>④ **视觉伺服对准（闭环）** | **8–10 周** | 砍掉就不成系统，**不可砍** |
| **加分** | ⑤ 上位机监控看板<br>⑥ INT8 量化调优 + 精度对比<br>⑦ **指标测量与可视化**（延迟/识别率/对准误差）<br>⑧ 数据存储 + 白名单 | +3–4 周 | 仍是完整毕设，只是"优秀"变"良好" |
| **拓展（争取）** | ⑨ 两级伺服（粗跟车 + 精对准牌）<br>⑩ 多目标巡检<br>⑪ 闸门/继电器联动<br>⑫ **自制 PCB 云台驱动板** | +4–6 周 | 不影响完整性 |
| **明确不做** | 完整桌面软件、云端平台、App、**自己训练识别模型**（用官方 LPRNet）、自研检测算法 | — | 明确写进"不做的范围" |

> 💡 **开题报告里就要写清"必做/加分/不做"**。
> 这样评审老师知道你有边界意识，而且**时间不够时你有正当理由砍**，而不是被判定"没做完"。

## 六、硬件清单与坑

| 项目 | 选择 | 参考价 | 备注 |
|---|---|---|---|
| **云台执行器** | 二自由度：**总线舵机**（推荐）或 **42 步进 + TB6600** | ¥150–400 | ⚠️ 见下方对比 |
| 云台机械结构 | 铝合金二轴云台支架 | ¥50–100 | 便宜，够用 |
| 摄像头 | USB 免驱 UVC 1080p（**装在云台上**） | ¥100–200 | 别碰 MIPI 排线 |
| STM32 开发板 | 你已有 | — | F4/F1 都行 |
| 电机电源 | **独立供电 12V/5V** | ¥30–60 | ⚠️ 见下方 |
| USB-TTL | CH340 3.3V | ¥15 | 备用/调试 |
| 继电器模块 | 演示闸门联动用 | ¥8 | 加分项 |

### ⚠️ 舵机 vs 步进电机

| | 舵机（SG90/MG996R） | 总线舵机 | 步进电机 |
|---|---|---|---|
| 难度 | 最简单（PWM 直驱） | 中（串口协议） | 高（需驱动器+细分） |
| 精度 | **差**（抖动、回差大） | 中 | **高** |
| **毕设适配度** | 能用，但**"精度"这个指标写不好看** | **推荐** | 最专业，能写"定位精度 0.1°" |
| 建议 | 先用它**跑通闭环**，再换 | ⭐ **性价比最优** | 想冲优秀论文选它 |

> **建议**：**先用 SG90 花 30 分钟跑通"识别→转过去"的闭环**，
> 再决定最终用舵机还是步进。**别一上来就啃步进驱动电路卡一周。**

### ⚠️ 两个经典坑（嵌入式 + 电机必踩）

1. **电机必须独立供电，并且和 STM32 共地**
   - 电机启动瞬间电流冲击会导致 STM32 **复位/死机**——你会怀疑代码，其实是电源
   - 现象：云台一转，串口就断、单片机重启
2. **PWM 与串口的定时器资源冲突**
   - STM32 的定时器数量有限，提前规划哪个定时器出 PWM、哪个做串口
   - 用 CubeMX 先看资源分配，别写到一半发现没定时器了

## 七、⭐ 技术亮点清单（这些是"加分"和"能写进论文"的东西）

按性价比排序：

| # | 亮点 | 为什么是亮点 | 成本 |
|---|---|---|---|
| 1 | **全链路延迟测量** | RK3588→串口→STM32→云台响应，**多少 ms**。能量化、能画图。**很多毕设完全没有量化指标，你一加档次就不一样** | 1 天 |
| 2 | **识别率对比实验** | 「固定摄像头」vs「云台主动对准」→ 一条曲线 | 2 天 |
| 3 | **自定义通信协议** | 帧头 + 长度 + 命令 + CRC16 + 超时重同步。**这是嵌入式系统该有的东西** | 1–2 天 |
| 4 | **FreeRTOS 任务设计** | 任务划分 / 优先级 / 队列 / 优先级反转 / 临界区。**你的主场，要讲透** | 已有基础 |
| 5 | **INT8 量化 + 逐层误差分析** | `accuracy_analysis()` 找敏感层 → 混合量化。**这是"研究"含量最高的一段** | 3–5 天 |
| 6 | **自制 PCB 云台驱动板** | STM32 + 驱动 + 电源 + 接口，**画一块板子 = 实物 + 论文里能放原理图/PCB 图** | 1–2 周 |
| 7 | **PID 工程细节** | 死区（消抖）、限幅、低通滤波、抗积分饱和。**能讲出这些说明你真的调过** | 已有基础 |
| 8 | **串口收帧：DMA + 空闲中断** | 不定长帧的标准做法，比"逐个字节中断"专业得多 | 半天 |
| 9 | **多线程取帧** | 取帧和推理分离，解决 USB 摄像头掉帧 | 1 天 |

> **指标要量化**，至少这几个：
> - 检测：mAP / FPS（NPU 实测）
> - 识别：字符准确率
> - 通信：帧率、丢帧率、**端到端延迟 (ms)**
> - 控制：**对准误差（像素 / 角度）**、稳态时间、超调量
> - 系统：连续运行 X 小时稳定性

## 八、时间线：和考研的关系（关键）

> ⚠️ **下面的推算基于"初试在 2027 年 12 月"这个假设**（你之前的说法里这点没确认）。
> 如果年份不同，把下面的年份整体平移即可，**结构不变**。

```
2026-09 ~ 12    ← 现在：RK3588 车牌识别跑通（M1–M9）
                  ★ 本质是毕设的【前期预研 / 技术验证】
2026-12-30      ← 项目工作窗口结束
2027-01 ~ 12    ← 考研备考（项目暂停）
2027-12         ← 初试
2028-01 ~ 06    ← 毕设 + 复试（同期！）
```

### 三个重要判断

**① 现在的项目 = 毕设的"预研"，这是巨大优势**

毕设最耗时间的部分（**RKNN 转换、算子适配、NPU 部署、量化掉点**）**你现在就在踩坑**。
等到毕设阶段，这些坑已经踩完了 —— **毕设的时间压力会小很多**。

**② 但要注意"不能直接复用"的问题**

有些学校要求毕设工作必须是**毕设期间完成**的，不能拿之前的项目直接交。
**解决办法**：毕设阶段做**扩展 + 系统化**，并在论文里明确区分：

| 论文里要分开写 | 内容 |
|---|---|
| **前期基础 / 预研工作** | RK3588 车牌检测与识别（2026 年完成） |
| **本设计工作** | 通信协议、云台视觉伺服、FreeRTOS 实时控制、系统集成与指标评测 |

**这不是"作弊"，这是正常的工程延续**——很多实验室的毕设都是建立在预研项目上的。
**但你必须在开题报告里就说清楚边界**，别等到答辩被问"这不是你之前做过的吗"。

**③ ⚠️ 最大的现实风险：毕设和复试同期**

2028 年 1–6 月你要**同时**：准备复试（笔试+面试+联系导师）+ 做毕设 + 答辩。
**这是整个规划里最紧的一段。**

**对策**：
- **毕设的"必做"部分必须在 2028-01 ~ 03 完成**（复试前）
- 复试时，**手里已经有一个能演示的系统** → 这就是最好的复试材料
- 3–4 月：复试 + 补"加分"项
- 5–6 月：写论文 + 答辩

> **反过来说**：如果毕设能在复试前跑通，**毕设和复试是互相加强的**——
> 复试老师最爱问"你的毕设做了什么"，你有一个能动的系统可以讲，
> 比"我做过一个车牌识别项目"强得多。

## 十、⚠️ 答辩可能被问的 10 个问题（提前准备）

| # | 老师会问 | 建议怎么答 |
|---|---|---|
| 1 | **车牌识别为什么要云台？为什么要跟踪？** | ★最可能被问。答"**视觉伺服**"：把车牌框与画面中心的偏差作为控制误差，主动对准提高识别率、扩大覆盖；**拿出识别率对比数据** |
| 2 | 为什么不在 PC 上识别，非要用 RK3588？ | 边缘部署：**延迟低、不依赖网络、数据不出场、功耗低、成本低**。有延迟对比数字更好 |
| 3 | **量化掉了多少精度？怎么补的？** | 给数字（如 mAP 掉 1.2%），讲**校准集质量**+**逐层误差分析**+**混合量化** |
| 4 | 检测和识别怎么分工？ | 两阶段：YOLO 定位车牌 → 裁剪 → LPRNet 识别字符。说清**为什么分两阶段** |
| 5 | 控制延迟多大？云台会不会抖？ | ★你的主场。讲**全链路延迟 ms 数** + **死区消抖** + **低通滤波** + **限幅** |
| 6 | **为什么用 FreeRTOS 而不是裸机？** | ★你的主场。多任务解耦、**优先级保障实时性**、可扩展。讲任务优先级设计、队列、优先级反转 |
| 7 | 串口丢帧/错帧怎么办？ | 帧头 + 长度 + **CRC 校验** + 超时重同步；讲**DMA + 空闲中断**收帧 |
| 8 | 光照差 / 车牌脏 / 角度偏怎么办？ | 诚实承认边界，说**云台对准正是为了缓解角度问题**，再补：补光、数据增强、多帧投票 |
| 9 | 和商用方案比有什么优势？ | 成本对比 + 开源可定制 + **边缘自主可控**。别吹"比海康好" |
| 10 | **你的创新点是什么？** | ⚠️ **诚实回答**：**不是算法创新**，是**系统集成 + 工程优化 + 量化评测**。**千万不要说"我提出了一个新算法"**——本科生提新算法基本会被当场拆穿，诚实反而加分 |

## 十二、一句话总结

> **题目不用换，它是好题目**——闭环、能演示、正好用上你全部技能栈。
>
> **但必须做三处调整**：
> 1. 把"**跟踪车牌**"改成"**云台视觉伺服主动对准**"（技术上站得住，还能量化）
> 2. 把"**上位机**"从控制闭环里**赶出去**，降级为监控看板
> 3. 功能分**必做 / 加分 / 拓展**三层，保证**砍掉也能交**
>
> **最大的风险不是技术，是工作量**——三个模块各自都是一个毕设。
> **最大的优势不是 AI，是你扎实的 STM32/FreeRTOS 功底**——
> 让答辩的主场留在你最强的地方。
