## 2. 七个坑：现象 → 定位 → 解决

| # | 现象 | 怎么定位的 | 解法 | 背后的规律 |
|---|---|---|---|---|
| 1 | `strings ... \| grep` 没任何输出 | `echo $?` → 退出码 1（没匹配）；`ls` 发现文件根本不存在 | 别纠结，改用现成脚本 | **"没输出"不是结论，退出码才是** |
| 2 | 模型 load 失败风险（runtime 1.4.0） | `strings librknnrt.so \| grep version` | 先看驱动版本（0.9.6）→ 只换运行库到 2.3.0 | **PC 工具链 / 板端 runtime / 模型 三者必须同代** |
| 3 | `git clone` 卡在 26%，`wget` 一直 await | 反复重试都失败 | `find /` 找现成的 | **要下载之前，先搜本机有没有** |
| 4 | conda 报 `Terms of Service have not been accepted` | `conda config --show-sources` → 只读了安装目录的配置 | 写 `~/.condarc` 配清华镜像 | **配置没生效时，先问"它到底读了哪个文件"** |
| 5 | `libtorch_cpu.so: undefined symbol: iJIT_NotifyEvent` | 搜官方论坛，确认是 torch↔mkl 不配套 | 造空壳 `libittnotify.so` + `LD_PRELOAD` | **有些符号你根本用不到，但加载器要先解析** |
| 6 | `No module named 'pkg_resources'` | 查代码发现工具链漏声明了 setuptools | `pip install "setuptools<81"` | **依赖清单不可信，要自己补** |
| 7 | `module 'onnx' has no attribute 'mapping'` | `python -c "import onnx; print(onnx.__version__)"` → 1.22.0（太新） | 降到 `onnx==1.14.1` | **新库会删老 API** |
| 8 | pip 报 `dependency conflicts ... protobuf` | **读它给出的具体要求**：`>=4.21.6,<=4.25.4` | 装 `protobuf 4.25.4` | **pip 的 `ERROR:` 常常只是警告，但内容必须读** |
| 9 | `cannot enable executable stack ... Invalid argument` | 报错指向 onnxruntime 的 `.so` | `patchelf --clear-execstack <那个.so>` | **老二进制 + 新内核 = 安全策略冲突** |
| 10 | 仿真报 `expect 'nhwc' like (1,640,640,3)` | 对照文档确认 `inference()` 默认 NHWC | 输入前 `np.transpose(x,(0,2,3,1))` | **框架之间的数据布局约定不同** |
| 11 | `load_rknn 的模型不能在 PC 上仿真` | 报错自己说清了：仿真只支持 `load_xxx→build` | 仿真必须在同一个会话里做 | **两种流程别混：转换/仿真 vs 部署** |

## 3. 提炼：环境问题排查六步法

1. **先分清"警告"和"错误"**
   `W`/`UserWarning`/`WARN` 通常可以忽略；`E`/`Error`/`Traceback` 才是要处理的。
   pip 那句 `ERROR: dependency conflicts` 其实只是警告——但**它给的版本要求必须读**。

2. **先确认前提存在，再谈别的**
   ```bash
   command -v 工具名     # 命令存在吗
   ls -l 文件路径        # 文件在吗
   ```
   七成的"怪问题"死在这一步（你的 `rknn_server` 就是根本不存在）。

3. **让命令自己说话**
   ```bash
   python -c "import 包; print(包.__version__, 包.__file__)"   # 实际用的是哪个、在哪
   conda config --show-sources      # 配置到底从哪个文件读的
   strings 二进制 | grep -i version # 二进制的真实版本
   ```

4. **逐字读错误里的"具体要求"**
   `expect 'nhwc' like (1,640,640,3)`、`requires protobuf<=4.25.4,>=4.21.6`——
   报错信息通常已经把答案写在脸上了，**别跳过它去搜索**。

5. **一次只改一个变量，看错误是否"往后推"**
   今天的错误顺序是：
   ```
   ModuleNotFoundError(import) → load_onnx 失败 → build 失败 → inference 失败
   ```
   **错误一路往后推 = 你在正确地前进**。如果报错原地打转，说明方向错了。

6. **先找现成的，再想下载**
   `find / -name '*.rknn'` 一个命令，省掉了整场"跟 GitHub 搏斗"。
   **例程、模型、二进制，往往早就在你机器上了。**

## 4. 版本代沟的三种形态（AI 部署的核心难点）

| 形态 | 表现 | 今天的例子 |
|---|---|---|
| **太老** | 老二进制在新系统上跑不起来 | onnxruntime 的可执行栈标记 |
| **太新** | 新库删了老 API | onnx 1.22 没有 `mapping` |
| **互相错配** | 两个包要求不同的版本 | torch ↔ mkl；onnx ↔ protobuf |

**对付它们只有一招：照官方测试过的组合把版本钉死**，而不是让 pip/conda"装最新的"。

## 5. 可复用的诊断命令清单

```bash
# ① 前提是否存在
command -v 工具名
ls -l 文件路径

# ② 命令到底成功没有
某命令; echo "退出码=$?"          # 0=成功 1=失败 127=命令不存在

# ③ 我用的是哪个包、哪个版本、在哪
python -c "import 包; print(包.__version__, 包.__file__)"

# ④ 配置从哪读的
conda config --show-sources
pip config list

# ⑤ 依赖到底要什么
pip show 包名 | grep -i requires
python -c "import importlib.metadata as m; [print(r) for r in (m.requires('包名') or [])]"

# ⑥ 二进制真实版本
strings 某个.so | grep -i version

# ⑦ 本机有没有现成的
find / -name '*.rknn' 2>/dev/null
find / -name 'librknn*' 2>/dev/null
```
